## 过程与证据边界

先调用 `list_scenarios`，再按指定参数调用 `new_game`。当前会话未直接挂载 tianbao 工具，故通过项目自带的 MCP 启动参数，使用 stdio JSON-RPC 调用同一服务的公开工具；`SIM_MCP_MODE=client`，存档目录限定在本次试玩目录。未直接调用引擎内部操作、未编辑存档、未回档、未重开，也未读取剧本隐藏参数来选策略。

逐季调用 `briefing` 和至少一次 `audience`，按照返回人设与可知事实在对话中扮演大臣；T0 另开廷议。每份诏书都先读拟诏回执，再单独调用 `confirm_edict`，有待决事件则显式 `choose` 后结算。公开复盘日志核验：每个决策季均有一次召对；十九份草案均有对应确认；三项待决事件均主动处理。原始工具请求及响应见 `transcript.jsonl`；服务导出复盘见 `public-log.json`；终局简报见 `final-briefing.md`。

## 决策复盘：预防为何失败

开局选择 `p_an_in_capital→keep`，担心立即夺镇引发“诸镇自危”，因此保留禄山官职、留京宿卫。T1 拒绝范阳请还帅后，也一直没有落实新帅接任及旧部三策安抚。这是本局的核心战略失误：把降低外重内轻、维持较低鼙鼓当成了足够的稳定条件，忽视了兵柄长期停在 60、旧部仍奉旧帅的风险。T7 使者已经实奏“拒命之迹已见”，之后未及时结束过渡状态。

T13 接受分兵进一步触动军中利益，紧接着结算即兵变；公开日志不能证明分兵是唯一触发条件，更不能从一次结果反推隐藏概率。其后依靠早期经营的河东、朔方与颜杲卿暗线，先守河北、再取范阳，两场战斗平乱，保全京师与财政。另一种预防策略是否能在同种子获最佳结局，本局没有重试验证。

## 所有遇到的问题及具体建议

### 1. 开局接入缺失与 Windows 管道权限（环境问题）

开局前，可调用工具目录中没有任何 tianbao 工具，通用 MCP 资源目录也没有该服务。没有据此伪造 `list_scenarios` 成功；改查本地接入文档，使用项目 `tools/mcp_call.py` 中的启动参数连接服务。

首次用官方 Python MCP SDK 的 `stdio_client` 启动时失败，尚未调用到游戏工具。调用链为 `anyio.open_process → asyncio.windows_utils.pipe → _winapi.CreateFile`，报 `PermissionError: [WinError 5] 拒绝访问`。改为同步 `subprocess.Popen` 标准输入输出及 JSON-RPC 后成功，首个游戏调用即 `list_scenarios({})`。这是运行环境的重叠管道限制，不能算作游戏规则错误。

建议：试玩入口先进行 MCP 健康检查，明确当前是否挂载服务、启动命令及存档目录；为受限 Windows 环境提供同步 stdio 客户端。服务冷启动等待较久时宜显示启动进度，避免无输出看似卡住。

### 2. T6 剧本选项固定免职，不能适配已改任的人事（实际规则回执错误）

T1 已通过自定义操作免国忠御史中丞并任颜真卿。T6 调用：

```json
{"adopted":[{"memorial_id":"t6_jiannan","option_id":"exile"}]}
```

实际该次草案还采纳继相等其他奏疏，并用 `appoint(chen_xilie, duzhi)` 补度支。`draft_edict` 返回草案 `edict-2a75d49f4330` 第 17 条：`[rejected] [INVALID_TARGET] 免 杨国忠 御史中丞；原因：该人物并未担任此官职`。确认后仍保留同一拒绝条款，其余任剑南、解度支等条款正常施行。

处置：不再对已不持有的官职重复免职，保留颜真卿现任，确认其余有效条款，国忠成功出镇。没有连续重试相同错误。建议剧本免职条款按当前持有者动态生成，或对“此人已不任该职”返回幂等的“无需执行”；组合任命也应汇总说明最终实际效果，避免把部分失败的一整项只记为“已处理”。

### 3. T6 哥安交恶叙述与实时位置矛盾

`briefing` 的 `t6_feast` 写“二人各在其镇”“本局二人不入京，改为致书”；`apart` 也写令二人各守其镇。但同份简报官职表、历季留京事实均显示安禄山在京畿，遥领范阳、平卢；哥舒翰才在陇右。确认后人物记忆仍写“令臣与禄山各守其镇”。

建议根据真实位置切换面见、致书、禁互讦的文本及选项说明；现有文本容易让人误以为此前留京失效。本次没有因此放禄山还镇。

### 4. T7 边镇加给宣称当次结算起支出，实际晚一次

`briefing` 的 `t7_border_notice` 明写“本季结算、入天宝十二载春时”起支国库；`halve` 为“本季结算起每季国库 −18”。本季草案 `edict-f07d690b61ac` 中这项没有 delayed。

T7→T8 的 `end_turn` 虽报“新增账目：边镇加给”，经常收支明细却不含 −18，国库经常净额为 +22。T8→T9 的结算才首次列出“边镇加给 −18”，经常净额 +4。这是文本与收费时点不一致。建议提前建账参与当次结算，或改明说从 T8 决策季结束的结算开始收费。

### 5. T14 行军中的军队在官职表被写成已驻目的地

T13 分出的陇右入卫兵在 T14 `briefing` 官职与兵权表里显示“10000（驻京畿）”，但同份简报在途段明确“自陇右赴京畿，约1季后到”。T14 `audience(yan_zhenqing)` 的摘要也明确其仍驻陇右、在途。`op_reference(entity_kind="armies")` 同样给出 `region=longyou`，`in_transit=自陇右赴京畿，约1季后到`。到 T15 才确实报抵达京畿。

建议军队表显示“赴京畿，在途”，区分出发地、目的地和已到驻地；否则部署京师防务时可能把未到的兵计入。

### 6. T0—T14 留京宿卫的长期兵变风险提示不足（可用性问题）

T0 `keep` 明示兵柄仍在、可能有“诸将请还帅”，立即夺镇选项则详细列出兵变概率与安抚三策。选择 keep 并拒还后，后来没有相应可直接采纳的旧部安抚奏疏；T13 分兵选项只列分兵与资源增减，未说明保留旧帅官职而长期羁留仍可能由史思明兵变。

T13 简报显示鼙鼓约 35—40、状态“承平”；T13→T14 却发生兵变，鼙鼓至约 66—71。公开导出的全部季报 `warnings` 均为空。低鼙鼓不能排除另一路兵变，玩法本身可以成立，但风险来源应分别展示。建议增加“旧部忠属/留京军心”风险条、持续提醒与可执行的平稳换帅路径，别让“承平”给出过强安全感。此条不否认我未完成解镇的决策责任。

### 7. T14 兵变首领不随军，导致可直接拘拿（机制合理性）

`end_turn` 将范阳军改隶大燕并交史思明，但史思明本人仍在唐廷控制的平卢，军队自行出兵河北。`op_reference(op="set_character_status")` 明确准许处置本朝臣属或身在本朝控制之地者。

因此我在 T14 提交 `{"op":"set_character_status","character":"shi_siming","status":"imprisoned","cause":"范阳兵变首逆，人在朝廷控制的平卢，命有司拘拿按问。"}`，草案 `edict-067b5a5c6cf1` 与确认均直接 applied，没有追捕、护卫或抵抗判定。完全按公开规则执行，但首领发动叛乱却留在可随时被拘的友方地盘，使其过于容易擒获。

建议兵变时同步处理首领位置、控制权与军队同行；拘拿敌方首领应判定当地实际控制和护卫，不只看地区控制旗标。

### 8. T16 善后叙述假定了本局没有做过的事

本局未采纳战时新募禁旅、赦囚发奴、流民入伍等选项；`s_demobilize` 却写“乱中新募之兵、赦囚奴仆之兵尚在行伍”。采纳 `release` 后回执固定禁军 −15000，并在下一季由 60000 降为 45000。实际上减的是现有禁军，未区分是否真有对应战时募兵。`s_finance` 也一概叙述军兴税商、鬻官、括富户，尽管本局没有采纳这些筹款方式。

复员与减税有益，所以本局仍采纳；问题在叙事与来源追踪。建议记录兵源及临时税目，只复员实际存在的相应兵员、只罢实际征收的税，或把选项改称一般裁军和整顿财计。

### 9. T17—T18 地区指标超过直觉量表，范围未说明

T17→T18 的结算直接报告“河北诸郡治安 +3（110→113）”。此前忠义、抚恤反复叠加，治安已超过 100。公开说明没有告诉我这是无上限指数还是百分量表。不能据此断言引擎算错，但玩家难以判断继续加治安是否有效。

建议在字段说明标出范围、软上限或边际效果；如本来是百分式量表，则统一裁剪并明确溢出。

### 10. 信息量与数字解释成本

每季 `briefing`、每次 `audience` 均重复整段扮演规则；目标段很长，混列未乱、兵变、乱平及延后终局条件。最初 `op_reference` 也很长，好在支持按 op 和实体过滤。建议增加简报 compact 模式，把规则首次展示后改成链接或短提醒，并按当前阶段优先展示目标。

数值对账整体能核对；出现的小额“取整差 ±0.1”已有明示，未把这些当成账目错误。事实中的数值往往是结算中间态，例如最终君威前有 83.8 的“赏罚分明”事实，实际再扣漂移后为 83.4；建议标注“结算中间态”，以免与期末值混淆。

### 11. 报告导出时的本地编码错误（辅助脚本问题）

终局导出复盘成功，文件已写入后，我的本地检查脚本尝试将含数学减号 `U+2212` 的片段打印到 GBK stdout，报 `UnicodeEncodeError: 'gbk' codec can't encode character '\\u2212'`。加 `sys.stdout.reconfigure(encoding='utf-8')` 后复查成功；游戏状态与导出内容没有损失。最初以 PowerShell 默认编码读接入 AGENTS 文本也有乱码，这是本地读取编码问题，不作为游戏文件损坏证据。

建议辅助脚本显式使用 UTF-8 读写和 stdout，Windows 用户文档也提供带编码的示例。

### 12. 终局后辅助连接清理的进程查询被拒（环境问题）

文件检查后，尝试用 `Get-CimInstance Win32_Process -Filter "Name = 'python.exe'"` 定位本次 `play.py --daemon` 进程以关闭辅助连接，系统返回“拒绝访问”，`HRESULT 0x80041003`。这是本机进程信息权限限制，不是 MCP 游戏工具错误。未据此批量终止 Python 进程，避免影响其他任务；原桥没有退出指令，最终向本次桥的自有请求队列发送 `requests:null`，有意使循环抛出 `TypeError: 'NoneType' object is not iterable` 并退出，由其 finally 关闭游戏服务 stdin、等待子进程退出。该异常仅用于结束本地辅助桥，没有提交任何额外游戏工具调用或改写存档。

建议辅助桥启动时记录自己的 PID，并支持显式 shutdown 指令，避免依赖全机进程查询。

## 错误与卡住情况汇总

实际规则拒绝只有 T6 上述 `INVALID_TARGET` 一项，拟诏和确认各显示了一次，属于同一条款。环境上遇到一次异步管道拒绝访问、一次报告打印编码错误，以及一次辅助进程查询拒绝访问，均已换方案或修正。没有同一个错误连续出现三次；没有调用终局后的 `end_turn`，没有发生 `GAME_OVER`、未确认草案阻断、待决事件逾期或永久卡住。
